Meet Chintu — Automating Data Lineage on Azure for $0.04 a Pipeline

Sarveshwaran RajagopalSenior Research Scientist
Session details

A senior director asked one question in a routine review: which source systems feed our churn model? A room full of engineers who had built the thing could not answer with confidence. We had 1,400 SQL pipelines, roughly three hours to trace each one by hand, and a backlog measured in thousands of engineer-hours. So we built Chintu — a multi-agent system using LangGraph and Azure OpenAI that automatically extracts, validates, and catalogs data lineage from SQL stored procedures. This session is the full, honest story of building Chintu — including the four walls we hit before it worked. Wall 1, The Bill: Our first prototype cost more per pipeline than manual tracing. I will show exactly how we cut cost from $0.42 to $0.04 per pipeline — structured JSON output instead of prose, complexity-based model routing so simple SQL never touches an expensive deployment, and the one prompt change that cut output tokens by 70%. Wall 2, The Kitchen: We sent 1,400 requests at once and the API stopped responding at 300. I will show the queuing, backoff, and checkpoint-resume patterns that cleared the backlog in 11 days. Wall 3, The Recipe: Security said our production SQL is not going to an external model. I will show the boundary architecture — what crosses the pass (table names, join structure) and what never does (literal values, credentials, customer data) — and the diagram that got security approval in one meeting. Wall 4, The People: Leadership paused the project in week three. The team wanted to know if they were being replaced. I will share the exact sentences that turned both conversations around. Live demo: You will watch Chintu process three SQL pipelines of increasing complexity in real time — see the scrubber strip sensitive values before anything leaves the network, the router pick a cheap or expensive model deployment, the extraction agent parse lineage, the validation agent catch errors, and the human approval gate fire only for the one pipeline where confidence is low. The audience decides whether to approve or reject. You will leave with a reusable architecture pattern for applying multi-agent AI to any enterprise automation problem — and the cost, security, and people playbook to get it into production.

Beyond GPUs: A Workload-First Framework for AI Compute and Data Centre Design

Aarrti TRJAI Lead
Session details

Enterprises scaling AI from pilot to production often default to "more GPUs" as the answer to every workload — quietly driving up cost, energy consumption, and time-to-deploy without ever asking whether the hardware actually matches the job. In a landscape where infrastructure decisions compound rapidly, this default is expensive, inflexible, and increasingly unsustainable. Choosing the right compute substrate — CPU, GPU, or TPU — is one of the highest-stakes architectural decisions an engineering team makes. Yet most teams lack a structured framework for making it well. This talk introduces a practical, workload-first decision framework grounded in three dimensions that matter most: workload shape, latency requirements, and power envelopes. We map these dimensions against the full spectrum of modern AI data centre architectures — each purpose-built for specific use cases rather than generic, one-size-fits-all deployments: • Dense GPU clusters — optimised for large-scale distributed model training • Hybrid CPU pipelines — delivering cost- and energy-efficient inference at scale • Disaggregated infrastructure (e.g., IBM LinuxONE) — purpose-built for data residency, compliance, and hybrid cloud workloads • Edge-to-core designs — engineered for latency-bound, real-time inference at the boundary • Ocean- and sea-based data centres — leveraging natural cooling environments to dramatically reduce energy and water footprint at scale Each model represents a deliberate architectural trade-off. Getting these decisions right pays off directly in time-to-market, sustainability metrics, and unit economics. Getting them wrong locks organisations into rigid, over-provisioned infrastructure that is costly to unwind. This session is designed for engineers, architects, and technical leads who need to move beyond instinct and vendor defaults — and make compute decisions they can defend with data. Key Takeaways 1. A workload-first decision framework for choosing between CPU, GPU, and TPU — based on workload shape, latency tolerance, and power constraints, not convention or vendor pressure 2. A practical map of purpose-built data centre models — from dense GPU clusters and disaggregated hybrid infrastructure to edge-to-core and ocean-cooled designs — and the specific use cases each one is engineered to serve 3. A framework linking infrastructure choices to business outcomes — connecting compute decisions directly to time-to-market, sustainability goals, and unit economics so technical teams can align with organisational priorities

The Machine-Readable Enterprise: Engineering the Context Layer

Vennila ShanmugamDirector of EngineeringCharan PanthangiLead AI Engineer
Session details

Enterprises already have enormous amounts of data spread across databases, lakehouses, event streams, documents, support systems, images, and other operational platforms. The challenge is no longer just storing or moving that data. The harder problem is giving machines a governed, queryable understanding of what the business actually is, including its entities, relationships, meanings, current state, and provenance. This session explores how modern data engineering can evolve from traditional pipelines into an enterprise context layer. The architecture combines multimodal ingestion, entity resolution, ontology engineering, knowledge graphs, temporal state, lineage, provenance, and runtime context assembly. A Knowledge Graph represents the persistent structure of the enterprise, including customers, products, contracts, suppliers, tickets, people, and the relationships between them. A Context Graph is then dynamically assembled for a specific question or decision, selecting only the relevant entities, facts, documents, events, and relationships from the larger enterprise knowledge base. Using a practical scenario such as identifying enterprise customers at risk of churn, the session demonstrates how structured data, support history, contracts, account relationships, product usage, and external signals can be combined into a small, evidence-backed context graph that is explainable and traceable to its original sources. The key idea is simple: The Knowledge Graph represents what the enterprise knows. The Context Graph represents what matters right now. The session presents a practical blueprint for moving from Data → Identity → Meaning → Knowledge → State → Context → Decision, and shows how the next generation of data platforms can become machine-readable foundations for analytics, applications, and AI.

The main focus of the talk is to show how current tools around mech interp for human-in the-loop AI model safety guardrails are fundamentally limiting - as they focus on text and linguistic channels to convert activations and outputs trained autoencoders into features.
